# Dependency Management Policy

**Status:** active · **Owner:** backend + frontend maintainers · **Introduced:** Stage 1 (T-1.5)

This document is the contract for how third-party code enters, moves and leaves
this repository. It covers both the Python backend and the Node frontend,
the audit gates in CI, and the process for accepting a finding that cannot be
fixed immediately.

---

## 1. Where the truth lives

| File | Role | Edited by |
|---|---|---|
| `backend/requirements.txt` | **Intent.** Direct dependencies with minimum-version ranges and the reasoning behind each choice. | A human, deliberately. |
| `backend/requirements.lock.txt` | **Reality.** Every package (direct *and* transitive) pinned to an exact version. This is what CI installs and what ships. | Generated — never hand-edited except for a documented security pin (§4). |
| `frontend/package.json` | **Intent.** Direct dependencies with semver ranges. | A human, deliberately. |
| `frontend/package-lock.json` | **Reality.** The full resolved tree with integrity hashes. | Generated by npm. |
| `backend/security/pip-audit-allowlist.yml` | Time-boxed, justified acceptances of known vulnerabilities. | A human, as a review decision. |

**Rule:** the lockfiles are the deployable contract. `requirements.txt` and
`package.json` describe what we *meant*; the lockfiles describe what actually
runs. Every CI job installs from the lockfile — including the Lighthouse job,
which until Stage 1 was still resolving the ranges and could therefore measure
a dependency set nothing else ever used.

---

## 2. Who bumps what

| Change | Who decides | What must happen |
|---|---|---|
| Patch/minor bump of a **transitive** package | Any maintainer | Regenerate the lockfile (§3), run the full suite, commit the lockfile alone. |
| Bump of a **direct** dependency within its declared range | Any maintainer | As above; no `requirements.txt` change needed. |
| Widening/raising a range in `requirements.txt` / `package.json` | Component owner | Justify in the commit message. Regenerate the lockfile. Run the full suite. |
| **Adding** a dependency | Component owner, with written justification | Must state why an existing dependency or the standard library will not do. Update the lockfile in the same commit. |
| **Removing** a dependency | Any maintainer | Remove from both intent and lock; check nothing imports it. |
| **Major** framework version bump (FastAPI, React, Vite, SQLAlchemy…) | Explicit project decision, its own stage | Never bundled into an unrelated task. Out of scope for hardening stages. |
| Security pin (raising a pin ahead of the resolver) | Any maintainer | Allowed as a direct lockfile edit **with a comment**; see §4. |

**Never** add a dependency and its lockfile update in separate commits — a
lockfile that does not match its intent file is worse than either alone.

## 3. Refreshing the lockfiles

### Backend (Python)

Regenerate after **any** `requirements.txt` change, and on the scheduled
refresh cadence (§6):

```bash
cd backend
python3 -m venv /tmp/lockvenv
/tmp/lockvenv/bin/pip install --upgrade pip
/tmp/lockvenv/bin/pip install -r requirements.txt
/tmp/lockvenv/bin/pip freeze > requirements.lock.txt
```

PowerShell (Windows):

```powershell
cd backend
python -m venv $env:TEMP\lockvenv
& "$env:TEMP\lockvenv\Scripts\pip.exe" install --upgrade pip
& "$env:TEMP\lockvenv\Scripts\pip.exe" install -r requirements.txt
& "$env:TEMP\lockvenv\Scripts\pip.exe" freeze > requirements.lock.txt
```

Then **verify and audit before committing**:

```bash
python scripts/verify_lock_install.py --strict-extra   # env == lockfile?
python scripts/audit_dependencies.py                   # any known CVEs?
pytest                                                 # does it still work?
```

> **`pip freeze` caveat.** `pip freeze` captures the build venv's *own*
> packaging tooling (`pip`, `setuptools`, `wheel`), which is not part of the
> application. Those lines are harmless but they are audited like everything
> else — this is exactly how the lockfile ended up pinning `setuptools==66.1.1`
> with three open advisories. If a refresh reintroduces a stale tooling pin,
> raise it (§4) rather than accepting the finding.

### Frontend (Node)

```bash
cd frontend
npm install          # updates package-lock.json within the declared ranges
npm ci               # verify a clean install from the lockfile
npm test && npm run build
npm audit --audit-level=low
```

CI uses `npm ci` exclusively: it installs strictly from `package-lock.json` and
fails if the lockfile and `package.json` disagree.

## 4. Security pins (direct lockfile edits)

Occasionally a package must be pinned **above** what the resolver picks —
typically packaging tooling captured by `pip freeze`, or a transitive package
whose parent has not yet released a fix. This is the only legitimate reason to
hand-edit `requirements.lock.txt`.

Requirements for such an edit:

1. A comment in `requirements.txt` (not just the lock) explaining the floor, so
   the next regeneration does not silently undo it.
2. `python scripts/verify_lock_install.py --strict-extra` passes in a venv
   built from the edited lockfile — proving the pin actually resolves.
3. `python scripts/audit_dependencies.py` passes.
4. The full backend suite passes.

**Current security pins**

| Package | Pin | Why |
|---|---|---|
| `setuptools` | `==84.0.0` | The Stage-07 lockfile carried `setuptools==66.1.1` (a `pip freeze` artefact of the build venv), which pip-audit flags for PYSEC-2025-49, PYSEC-2026-1918 and PYSEC-2026-3447. Nothing in `app/`, `ai/` or `scripts/` imports setuptools or `pkg_resources` at runtime, but shipping a lockfile with known advisories is not acceptable and allowlisting a trivially fixable finding sets the wrong precedent. Raised to the first version fixing all three. |

## 5. Audit gates

### Backend — `scripts/audit_dependencies.py`

Runs in the CI `backend` job. It audits **`requirements.lock.txt`**, not
`requirements.txt`:

> Auditing a file of ranges audits whatever resolves *at audit time*, which is
> neither what CI installs nor what deploys. A vulnerable pinned version can
> sail through a clean range audit.

Findings are reconciled against `security/pip-audit-allowlist.yml`. The gate
fails on:

- any finding with no matching allowlist entry;
- an allowlist entry that is **expired** (`expires` in the past);
- an allowlist entry whose `expires` is more than **180 days** out;
- an allowlist entry missing `id`, `package`, `reason`, `owner` or `expires`;
- (with `--strict-stale`) an allowlist entry that no longer matches any
  finding — so the list cannot rot after an upgrade fixes the issue.

Run it locally exactly as CI does:

```bash
cd backend
pip install pip-audit pyyaml
python scripts/audit_dependencies.py
```

### Accepting a finding

Allowlisting is the **last** option, after (1) raising the pin and (2) replacing
the dependency. To accept one, add an entry:

```yaml
allowlist:
  - id: PYSEC-2026-1234
    package: some-package
    reason: >-
      The vulnerable code path is the XML parser, which we never call — our only
      use is `some_package.encode()`. Upstream fix expected in 3.2.0.
    owner: backend-maintainer
    expires: 2026-11-30
    ticket: IR-S1-00X
```

`reason` must describe **reachability in this codebase** — "low severity" or
"dev dependency" is not a justification. The expiry is mandatory and capped at
180 days: an acceptance nobody has revisited in six months is not an accepted
risk, it is a forgotten one.

The allowlist is currently **empty**, which is the desired steady state.

### Backend — `scripts/verify_lock_install.py`

Also in the CI `backend`, `multi-worker`, `e2e` and `lighthouse` jobs. It
compares `pip freeze` against the lockfile and publishes the diff as the
`backend-lock-verification` artifact (JSON + log + the freeze itself), so
"we install the locked set" is an artifact you can open, not a claim.

- `MISSING` (pinned, not installed) → fail
- `MISMATCH` (different version) → fail
- `EXTRA` (installed, not pinned) → reported; fails only with `--strict-extra`,
  which the jobs use *before* layering CI-only tooling (`ruff`, `pip-audit`).

### Frontend — `npm audit`

The CI `frontend` job runs `npm audit --audit-level=low`. npm has no equivalent
allowlist mechanism here; if a finding cannot be fixed, record it in
`integration-request.md` with an owner and a date, and reference it in the PR.
There is currently **0** finding.

## 6. Audit cadence

| Activity | Frequency | Owner |
|---|---|---|
| `pip-audit` + `npm audit` gates | **Every CI run** (every push and PR) | automated |
| Locked-install verification | **Every CI run** | automated |
| Allowlist expiry check | **Every CI run** (an expired entry breaks the build) | automated |
| Lockfile refresh (`pip freeze` / `npm install`) | **Monthly**, and always before a release tag | maintainers |
| Direct-dependency review (are these still the right choices?) | **Per release** | component owners |
| Major-version upgrade review | **Per quarter**, as its own scheduled work | project decision |

A release must not be tagged with an expired or stale allowlist entry.

## 7. Frontend test tooling and Playwright browsers

The E2E suite needs a real Chromium binary, which is **not** installed by
`npm ci` — it is a separate download (~150 MB) into a per-user cache.

```bash
cd frontend
npm ci
npx playwright install chromium          # first run only
npm test                                 # Vitest unit suite
npm run e2e                              # Playwright suite
```

### Windows / PowerShell

```powershell
cd frontend
npm ci
npx playwright install chromium

# The specs read E2E_BASE_URL; set it for the session if the app is elsewhere:
$env:E2E_BASE_URL = "http://localhost:5173"
npm run e2e
```

`--with-deps` (used in CI) installs Linux system libraries via apt and is a
**Linux-only** flag; on Windows and macOS use plain
`npx playwright install chromium`.

Browsers are cached outside the repo:

| OS | Cache location |
|---|---|
| Linux | `~/.cache/ms-playwright` |
| Windows | `%USERPROFILE%\AppData\Local\ms-playwright` |
| macOS | `~/Library/Caches/ms-playwright` |

Override with `PLAYWRIGHT_BROWSERS_PATH`. To pre-seed an air-gapped machine,
copy that directory from a machine with egress.

> **Known blocker (IR-S1-001).** The Stage-1 development sandbox cannot reach
> `cdn.playwright.dev` (TLS `ECONNRESET`), so the browser cannot be downloaded
> and the Playwright suite cannot be executed locally there. It runs in the CI
> `e2e` job, which has egress. Verbatim failure output:
> `docs/agent-reports/stage1-evidence/t-1.4b/00-browser-download-blocked-retry.log`.
> The E2E specs' backend contracts are additionally verified locally at the
> protocol layer by `stage1-evidence/t-1.4b/03-journey-protocol-harness.mjs`.

The Playwright **package** version (`@playwright/test` in `package.json`) and
the **browser build** it downloads are coupled: bumping the package generally
requires re-running `npx playwright install chromium`. CI does this on every
run, so no cached-browser drift is possible there.

## 8. Adding a dependency — checklist

- [ ] Can the standard library, or something already in the lockfile, do this?
- [ ] Is it actively maintained (recent releases, open issue triage)?
- [ ] Licence compatible with the project?
- [ ] Does it pull a large transitive tree? (`pipdeptree` / `npm ls`)
- [ ] Added to `requirements.txt` / `package.json` **with a comment saying why**
- [ ] Lockfile regenerated in the **same commit**
- [ ] `verify_lock_install.py` and `audit_dependencies.py` pass
- [ ] Full test suite passes
- [ ] If it needs configuration: `.env.example` updated, no secrets committed
